HOW IT WORKS

From sign-up to a live cluster in about two minutes

No desktop app, no kubeconfig upload, no Helm chart. You run one command against your cluster and open the dashboard.

01

Sign up

Create an account at clusterheart.com. Each cluster you add gets its own ID and agent token.

02

Add a cluster

Name it, then paste the generated command. It creates a namespace, a secret and the agent.

kubectl apply -f \
  https://clusterheart.com/agent.yaml
03

Open the dashboard

Within 30 seconds the cluster shows as Connected. Add as many clusters as you run and switch between them.

THE AGENT

One small pod that watches your cluster for you

The agent runs as a single pod, clusterheart-agent, in its own clusterheart-sre namespace. Every 30 seconds it does the same loop, then goes back to sleep. It asks for 25m CPU and 64Mi of memory.

What it can do
✓Read nodes, pods, events, workloads and jobs
✓Read live CPU and memory from metrics-server
✓Read the logs of failing pods
✓Spot secrets leaked into logs or pod specs
What it can't
✕Change, delete or restart anything
✕Read Secrets or ConfigMaps, exec into pods, port-forward
✕Accept inbound connections: it only calls out over HTTPS
  1. 1

    Reads the cluster state

    Lists nodes, pods, Deployments, StatefulSets, DaemonSets, Jobs and recent warning events through the Kubernetes API, using a read-only ServiceAccount.

  2. 2

    Measures real usage

    Pulls live CPU and memory for every pod and node from metrics-server, plus each pod's requests and limits, so usage can be compared with what was asked for.

  3. 3

    Detects what's broken

    Flags CrashLoopBackOff, OOMKilled, ImagePullBackOff, unschedulable pods and stuck rollouts from the pods' own status. Nothing is guessed.

  4. 4

    Reads the logs of failing pods

    For crashing, OOMKilled and failed pods it reads the last lines, from the instance that crashed, so you see what happened right before the restart.

    web/api-7c9f · before last restart
INFO  connecting to postgres at db.web.svc:5432
ERROR dial tcp 10.0.3.14:5432: connection refused
panic: database unavailable after 3 retries
  5. 5

    Looks for leaked secrets

    Checks every pod spec for passwords and keys typed straight into env vars or command args, and scans the new log output of every running container, a few containers each cycle. It reports where a secret is and what kind (an AWS key, a private key, a password in a URL), never the secret itself.

  6. 6

    Scrubs secrets

    Before anything leaves the cluster, bearer tokens, JWTs, cloud keys, passwords in key=value form, credentials in URLs and email addresses are replaced with [REDACTED]. The server scrubs again on arrival.

  7. 7

    Sends one snapshot

    Posts the snapshot over HTTPS with its own token. If the connection drops, it buffers and catches up when it's back.

  8. ✓

    You get answers, not raw data

    Clusterheart turns those snapshots into a health view, incidents with an AI root-cause analysis, rightsizing suggestions from 6 hours of peaks, and a history of everything that changed.

IN THE DASHBOARD

Everything about your cluster, one tab away

Pods, health, sizing, incidents and an assistant that knows your cluster, for every cluster you connect.

Live pods, nodes and jobs

Every pod with status, restarts and live CPU and memory. Node pressure at a glance. Jobs grouped per CronJob, so a job reads failed only when its last run failed.

Health with the logs

Problems and warning events in one place, with the last log lines of every failing pod right underneath. No more kubectl logs --previous hunting.

Incidents and AI root cause

Problems become incidents automatically. One click runs a diagnosis over the evidence and logs: what happened, likely causes, a suggested fix and how to roll it back.

Rightsizing you can apply

Requests compared with the 6-hour peak of each workload. Suggestions are peak plus 20%, with a copyable command or an Apply button. System add-ons are marked Managed and left alone.

Fixes you approve

Restart, scale or resize a workload through an opt-in controller, only after you approve. Policy checks, cooldowns, an emergency pause and the previous values for rollback are built in.

Leaked secret detection

Finds AWS keys, private keys, tokens and passwords printed in logs or hard-coded into env vars and args, with severity and the exact fix: rotate it, or move it into a Secret.

A history of every change

Every proposal, approval, rejection, applied fix and pause is logged with who did it and when, per cluster.

All your clusters in one place

Production, staging and every other cluster side by side, each with its own agent and token. Remove one from the dashboard with a click.

An assistant that knows your cluster

Ask in plain language. Answers are short bullets rated green, yellow or red, each quoting the metric or log line behind it. Your last chats are saved.

SAFE BY DEFAULT

Read-only until you say otherwise

Watching and changing are separate. The agent can only look. Changes go through a second, opt-in controller with its own narrow permissions, and only after a person approves them.

01
Your cluster stays closed
The agent only makes outbound HTTPS calls. No inbound ports, no VPN, no kubeconfig shared with us.
02
Every change is a person's decision
The AI can suggest a fix but never apply one. You approve each change, and it's recorded with your name in Activity.
03
Guardrails on every fix
Emergency pause, one change at a time, a 10-minute cooldown per workload, a circuit breaker after failures, and platform namespaces off limits.
04
Easy to remove
Delete the clusterheart-sre namespace and its two cluster roles, and nothing of ours is left in your cluster.
